## 二、宿舍视觉方向——本次最重要的要求

**宿舍当前暂定使用正视广角视角，而不是等距视角、45°斜俯视或纯俯视。**

### 2.1 预期视觉体验

玩家仿佛站在房间前方，透过一个较宽的视野，向真实的房间内部观看。

画面应体现：

1. 镜头基本正对房间内部。
2. 能够看到房间后墙、左右侧墙，以及具有纵深感的地面。
3. 通过墙面、地面、家具的透视关系表现空间深度。
4. 家具前后位置清晰，整体构图符合统一的透视逻辑。
5. 观感接近观看真实房间，而不是观看一个斜上方的房间模型。
6. 视野相对宽广，但不刻意追求鱼眼效果、极端透视或明显的边缘扭曲。
7. 玩家能够理解家具位于房间的前方、中部还是后方。
8. 即使使用简单几何图形，也应能辨认房间的空间结构。

### 2.2 明确禁止的偏离

- 不得把宿舍默认设计成等距视角。
- 不得采用 45°斜俯视房间作为主要表现方式。
- 不得以纯俯视平面地图替代室内空间。
- 不得简单堆叠平面按钮来冒充家具空间。
- 不得通过非等比拉伸制造空间纵深。
- 不得自行更换宿舍镜头方向。
- 不得将灰盒占位效果视为正式美术。

**正视广角属于镜头与构图要求，不等同于必须使用 3D 引擎实现。**

本次应优先验证 2D 分层与透视绘制方案。

## 三、本阶段核心目标

本阶段不是制作正式宿舍，而是验证以下七个问题：

1. 使用低成本技术，能否实现可信的正视广角房间空间？
2. 家具能否在该视角下自然地表现前后纵深？
3. 家具之间及家具与测试对象之间的遮挡是否正确？
4. 家具位置改变后，遮挡关系能否正确更新？
5. 同一房间能否适应 PC 横屏和手机竖屏？
6. 鼠标、触摸和遮挡区域的交互是否准确？
7. 2D 分层是否足够，还是存在必须进一步验证局部 3D 的技术理由？

优先验证技术可行性、可维护性和美术生产成本。

不要以追求画面精美为由扩大开发范围。

## 四、宿舍灰盒场景要求

建立一间最小可交互宿舍。

### 4.1 房间结构

至少包含：

- 一面后墙。
- 左右侧墙。
- 一块具有空间纵深感的地面。
- 必要的墙面与地面交界线。
- 与正视广角一致的基础透视关系。

可以通过简单颜色、线框和几何图形区分空间层次。

不要求正式纹理、贴图、光照或装饰。

### 4.2 家具

放置三件几何家具，例如：

- 床
- 书桌
- 衣柜

每件家具需要具备：

- 唯一的内部标识。
- 明确的空间位置。
- 可见的占地和遮挡范围。
- 用于简单交互的点击区域。
- 可更换占位美术的场景结构。

家具外形应能辅助判断深度，而不是只有没有空间信息的平面矩形。

### 4.3 测试标记物

增加一个可以移动的测试标记物，用于验证：

- 位于家具前方。
- 位于家具后方。
- 穿过家具前后遮挡边界。
- 在不同家具之间移动。
- 位置改变后是否正确显示或遮挡。

测试标记物不是正式玩家角色，也不是猫咪系统。

不需要建立角色移动系统、寻路系统或宠物 AI。

## 五、空间透视和遮挡技术实验

优先使用 Godot 原生 2D 技术。

可以考虑：

- Node2D
- CanvasItem 绘制
- 分离的前景与背景图层
- Y-sort（适用时）
- 多层遮挡区域
- 固定透视参数
- 简单的 2D 几何变换

以上只是允许采用的技术手段，并非要求全部实现。

### 5.1 必须验证的情况

1. 家具位于不同深度时的显示顺序。
2. 测试标记物移动到床后方时的正确遮挡。
3. 标记物移动到家具前方后恢复可见。
4. 家具与家具重叠时的层次处理。
5. 至少一件家具改变位置后，遮挡正确更新。
6. 家具视觉区域与点击检测区域保持对应。
7. 家具在正视广角透视下保持一致的空间关系。

### 5.2 技术取舍

不要默认 Y-sort 就能解决所有家具遮挡。

如果单一排序规则不足以处理高家具、局部遮挡或复杂形状，可以使用有限的前后分层或遮挡切片。

避免在未验证之前建立复杂的通用深度管理器。

如果出现 2D 技术明显难以解决的问题，需要记录：

- 问题现象。
- 可复现条件。
- 2D 解决方案。
- 可能的局部 3D 备选。
- 对美术生产与维护成本的影响。

未经项目负责人确认，不得把房间改为完整 3D。

## 六、PC 横屏与手机竖屏适配

宿舍在两个平台上必须保持**相同的正视广角空间方向**。

允许使用不同的取景与 UI 布局，但不得将手机竖屏改成俯视或等距视角。

### 6.1 PC 横屏

目标是：

- 展示较完整的房间空间。
- 家具之间保持清晰的前后关系。
- 玩家容易理解整体布局。
- 点击区域和操作反馈清楚。
- UI 不大面积遮挡房间。
- 画面不出现明显透视错乱。

### 6.2 手机竖屏

重点解决：

- 横向可视空间有限。
- 家具可能变得过小。
- 透视关系可能不容易辨认。
- UI 与房间物品可能重叠。
- 触摸热点可能密集。

允许实验：

- 独立的竖屏构图。
- 合理的镜头缩放。
- 受约束的横向平移。
- 局部聚焦。
- UI 重排。

这些方案均应保留同一个空间模型，不要重复制作两套不兼容的房间数据。

如使用平移或局部聚焦，必须有明确的操作和返回方式，避免增加不必要的交互负担。

不得为适配竖屏直接裁掉所有重要家具。

### 6.3 分辨率验证

至少测试：

| 模式 | 尺寸 |
|---|---|
| PC 16:9 | 1920×1080 |
| PC 16:10 | 1280×800 |
| 手机竖屏模拟 | 1080×1920 |
| 长屏手机模拟 | 1170×2532 |
| 小屏逻辑基准 | 360×780 |

所有模拟视口测试必须与真实设备测试明确区分。

如果没有 Android 真机，不得声称真机触摸或安全区已验证。

## 七、最小交互功能

只实现支持技术实验的必要交互：

1. 点击家具显示名称或简单状态。
2. 使用简化操作调整至少一件家具的位置。
3. 移动测试标记物并观察遮挡变化。
4. 从宿舍返回城市地图。
5. 在横竖屏切换后继续操作。

家具移动仅用于测试空间关系。

不开发正式家具收纳、每日任务、房间装修或购买系统。

也不开发正式猫咪玩法。

## 八、与现有主工程集成

本次灰盒应通过当前地图中的宿舍建筑入口访问。

要求：

1. 保持现有宿舍建筑稳定 ID。
2. 保持 BuildingDefinition 与地图导航接口。
3. 不改变学校和商店既有行为。
4. 返回地图后保留此前约定的导航状态。
5. 保留已有点击与场景转换防护。
6. 不新增不必要的全局管理器。
7. 不建立大型通用家具系统。
8. 灰盒美术可替换，不应与核心逻辑高度耦合。
9. 不增加正式存档、经济、任务等依赖。

如果现有临时宿舍交互被替换，必须保留地图导航语义，并合理更新受影响的测试，不得直接删除原有正确性保障。

## 九、测试和回归要求

### 9.1 既有系统回归

运行：

- P0-02 Headless 测试。
- P0-02 Windows Rendered 测试。
- 既有连续稳定性测试。
- 地图、学校、商店、宿舍导航回归。
- 横竖屏切换与重复输入回归。

如宿舍场景变化使旧测试不适用，应更新测试以检查等价的功能合同，并记录调整原因。

不得删除测试以制造通过率。

### 9.2 新增空间测试

验证：

1. 宿舍场景加载成功。
2. 三件家具全部可见并可交互。
3. 测试标记物能够移动。
4. 家具遮挡规则符合空间位置。
5. 家具换位后遮挡更新正确。
6. 点击区域与物体视觉位置一致。
7. 横竖屏切换不破坏场景。
8. 可正常返回地图。
9. 鼠标与合成触摸交互正确。
10. 没有明显的错误引用或节点残留。

允许增加针对深度排序、空间状态和输入的自动化断言。

### 9.3 视觉验收证据

必须实际运行 Godot 并保存渲染截图，至少包括：

- PC 横屏整体宿舍。
- 手机竖屏模拟宿舍。
- 标记物在家具前方。
- 标记物在家具后方。
- 家具换位后的遮挡。
- 必要的透视或布局问题对比。

**程序断言通过不等于视觉空间方案通过。**

如果无法进行人工可视化操作，应明确说明，只提供实际渲染截图和可复核的测试证据。

不能用程序内部参数证明画面一定符合视觉目标。

## 十、最终技术评估

完成后，必须明确回答：

1. 正视广角的空间感是否初步成立？
2. 当前 2D 分层方式是否满足该视角？
3. 墙面、地面和家具的透视是否协调？
4. 家具遮挡的主要限制是什么？
5. 家具移动是否会带来高维护成本？
6. 手机竖屏是否需要专门的取景机制？
7. 该方案是否可以支持未来的猫咪藏身与物品互动？
8. 是否有充分理由再做局部 3D 实验？
9. 预计正式美术制作的主要技术约束是什么？
10. 哪些选择需要项目负责人根据截图决定？

上述问题应基于原型结果回答，不得把没有实验的推测写成已验证事实。

本次只提出是否建议继续采用正视广角的意见，不得自行认定视觉方案正式定稿。
