## 二、阶段划分与执行顺序

### P0-02A：稳定性问题诊断

先复现 P0-01 遗留的原生渲染测试失败。

要求：

1. 阅读项目 `AGENTS.md`、P0-01 开发报告、测试报告和基线收尾记录。
2. 检查当前 Git 工作区状态及未提交文件。
3. 阅读地图导航、建筑热点、横竖屏布局、安全区域和测试脚本的相关实现。
4. 使用现有测试命令复现故障。
5. 对失败增加必要的诊断日志，记录窗口尺寸、逻辑视口、布局方向、按钮位置、输入坐标、焦点及导航状态。
6. 检查布局是否在同一帧内部分更新，输入是否在布局稳定前发生。
7. 检查是否存在事件重复触发、焦点竞争、测试等待不足、窗口切换异步时序等问题。
8. 根据证据判断是游戏逻辑缺陷、测试工具缺陷、环境限制，还是多个原因共同导致。

**禁止在没有证据时直接认定是自动化测试不稳定。**

不得通过删除测试、放宽正确性断言、固定错误布局或掩盖日志来制造通过结果。

### P0-02B：最小修复与回归

根据诊断结果修复实际发现的问题。

重点包括：

- 导航进入和返回的可靠性。
- 点击热点与实际显示位置一致。
- 横屏及竖屏布局更新的完整性。
- 画面重排与输入响应的时序协调。
- 窗口尺寸变更后的交互可靠性。
- 商店锁定状态和提示反馈。
- 重复点击与异常场景配置防护。

要求：

1. 优先最小修改，避免无关重构。
2. 保持原有建筑稳定 ID 与 Resource 数据结构。
3. 保持地图和建筑内部场景的模块边界。
4. 针对实际故障补充回归测试。
5. 保留修复前后的失败记录，禁止覆盖重要证据。
6. 若发现测试脚本错误，允许修正，但必须解释原因并证明未降低验收要求。

修复后执行：

- 全套 Headless 测试。
- 全套 Windows Rendered 测试。
- 多次重复 Rendered 测试，至少连续 5 轮通过。
- 横竖屏连续切换测试。
- 建筑进入、交互、返回的连续循环测试。
- 必要的人工可视化操作检查。

连续通过并不代表绝对不存在偶发故障。如果仍有间歇性失败，应记录失败频率、触发条件和当前证据。

### P0-02C：建立 Git 稳定基线

只有满足以下要求后，才创建稳定版本基线：

- 已发现的阻断性问题已修复，或者能够提供明确证据证明问题仅属于测试环境且产品行为不受影响。
- Headless 测试全部通过。
- Windows Rendered 测试达到上述连续稳定性要求。
- 主入口可以正常运行。
- 工作区不存在不应该提交的缓存、工具程序、密钥或签名文件。
- `.gitignore` 正确排除 `.tools/`、`.godot/`、构建输出和敏感配置。

然后：

1. 使用已授权的本地 Git 作者信息。
2. 创建本地稳定基线提交。
3. 记录完整 commit ID。
4. 不创建远程仓库。
5. 不擅自推送到 GitHub 或其他平台。
6. 不将大型工具下载包加入仓库。

如果稳定性验收无法通过，则保留修复工作和诊断结果，不得虚构稳定基线或继续扩大开发范围。

### P0-02D：Windows 发行包验证

完成稳定基线后，再进行 Windows 构建工作。

要求：

1. 安装或配置与当前 Godot 版本一致的官方导出模板。
2. 建立 Windows 测试导出预设。
3. 导出可以脱离 Godot 编辑器运行的 Windows 程序。
4. 在实际 Windows 环境中启动导出程序。
5. 测试地图、宿舍、学校、商店和返回逻辑。
6. 检查横屏显示、基本输入、缺失资源及退出行为。
7. 记录构建产物路径、体积、测试结果和日志。

不得仅凭编辑器内运行成功宣称 Windows 发行版本验证成功。

### P0-02E：Android 构建与竖屏验证

首先检查 Android 开发工具链。

需要核实：

- JDK 版本。
- Android SDK 和必要组件。
- Godot 对应版本导出模板。
- Android 导出配置。
- 测试签名方案。
- 当前可用的模拟器或真实设备。

在环境允许并符合官方工具要求的情况下：

1. 配置 Android 调试导出预设。
2. 生成可安装的 APK。
3. 检查导出过程是否成功。
4. 如果有 Android 测试设备，安装并运行。
5. 如果有模拟器，执行模拟器验证。
6. 检查手机竖屏界面和地图建筑交互。
7. 验证触摸输入与点击位置一致。
8. 验证 Android 返回操作。
9. 检查屏幕安全区域、导航栏和系统手势区域。
10. 检查切换后台、恢复前台后的状态。
11. 记录基础性能、启动表现、加载异常和崩溃情况。

应记录测试设备或模拟器的系统版本、屏幕参数、测试方式与结果。

**必须严格区分：构建通过、模拟器通过和真机通过。**

如果缺少 SDK、模拟器或设备：

- 记录阻碍条件。
- 可完成不依赖该条件的配置与检查。
- 不擅自使用不可信工具或购买服务。
- 将未完成的验证列为阻断相应平台发布的风险。

不得将 Android APK 构建成功等同于真机兼容性通过。

### P0-02F：macOS 与 iOS 可行性记录

项目仍以 Windows、macOS、Android、iOS 为长期目标。

当前 Windows 环境不具备 macOS/Xcode 条件时：

1. 检查当前技术方案是否引入明显不兼容的系统依赖。
2. 核实需要的 macOS、Xcode、Apple 开发者签名与导出条件。
3. 记录未来实际构建和设备测试所需的环境。
4. 不得宣称 macOS 或 iOS 已经通过验证。
5. 不为缺少当前环境而提前建立复杂的远程构建服务。

本阶段允许 macOS/iOS 保持未验证，但必须将对应验证列为未来平台发布前的必要条件。

## 三、横竖屏与输入验收

PC 端以横屏体验为主要目标；手机端以竖屏体验为主要目标。

两种布局应共用：

- 建筑数据。
- 场景导航逻辑。
- 建筑解锁状态。
- 基础交互语义。

允许分别维护地图布局和 UI 构图。

不得仅通过非等比拉伸画面满足屏幕适配。

至少保留以下模拟尺寸的验证：

| 模式 | 测试尺寸 |
|---|---|
| PC 横屏 | 1920×1080 |
| PC 横屏 | 1280×800 |
| 手机竖屏模拟 | 1080×1920 |
| 长屏手机模拟 | 1170×2532 |
| 小屏逻辑基准 | 360×780 |

补充检查窗口切换时的布局稳定性及输入触发时序。

真机测试时，必须使用设备实际安全区和触摸反馈结果，不能仅以桌面模拟替代。

## 四、技术风险与架构要求

继续维护现有风险登记表。

本阶段重点风险：

1. 原生窗口布局刷新与输入时序。
2. 不同宽高比的热点定位。
3. 实际触摸与鼠标模拟的行为差异。
4. Android 工具链与导出兼容性。
5. 手机安全区域及后台恢复。
6. 不同设备的实际性能。
7. Windows 和 Android 导出资源完整性。
8. 未来 macOS/iOS 的构建和签名依赖。

本阶段不开发正式宿舍美术、猫咪玩法、每日整理、剧情、NPC、俄语教学、宠物成长、背包、经济、联网或完整存档系统。

不得为了未来设想编写大型通用框架。

保留 DEMO 与正式版共享主工程的策略。

## 五、交付和报告规范

从本阶段开始采用统一交付制度：

**一个阶段，对主线只提供一份汇总报告。**

请生成：

`docs/reports/P0-02_SUMMARY.md`

该报告必须包含：

1. 本阶段总体结论与完成状态。
2. P0-01 遗留问题的根因、修复方法和验证结果。
3. 实际修改的代码及配置文件。
4. Headless、Rendered 和重复稳定性测试结果。
5. Git 基线提交 ID，以及本阶段最终提交 ID（如已提交）。
6. Windows 导出及实际运行结果。
7. Android APK、模拟器和真机验证结果。
8. macOS/iOS 未完成项目与原因。
9. 已解决、未解决和新增的风险。
10. 测试日志、截图、构建产物的项目内相对路径。
11. 对下一阶段宿舍空间灰盒的建议。
12. 需要项目负责人决策的事项。

完整日志、原始测试 JSON、截图、风险登记表及架构决策记录应保留在本地项目对应目录。

汇总报告只引用这些文件，不需要复制全部内容。

如测试失败，汇总报告也必须如实反映，不能因阶段未通过就不提交报告。
