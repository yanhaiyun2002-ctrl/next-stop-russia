# P0-01：技术可行性审查＋第一层级地图主工程

项目：《下一站，俄罗斯！》；阶段：Pre-production P0。项目仅有计划，没有正式游戏代码。

## 工作边界与顺序

1. **P0-01A（先执行）**：审查 `TECH_BASELINE.md` 与 `FEATURE_FEASIBILITY.md`，确认引擎、导出限制及可能导致重大返工的风险，产出风险报告。
2. **P0-01B（条件通过后）**：若未发现明确的关键阻碍，创建最小 Godot 主工程，地图作为真实的首层场景入口。
3. 如果发现阻断性技术冲突，暂停相关高风险开发，提交证据、替代方案与决策请求；不得私自切换引擎。

## A. 技术可行性审查

- 用 Godot 相应版本官方资料或实际最小实验评估引擎、GDScript、Compatibility 渲染器与 PC/手机平台适配。
- 对功能清单逐项分类：已验证/原则上可行未验证/高风险需原型/外部依赖/信息不足。
- 将**PC 横屏、手机竖屏、房间分层空间、家具遮挡、拖放、俄语字体与音频、未来语音功能、存档迁移**列为重点。
- 明确每项风险的可能性、影响、证据、最小验证方法、备选方案与应解决的里程碑。
- 不保证未知功能全能实现，不以支持文档取代实机测试。
- 结果写入 `docs/TECH_FEASIBILITY.md` 和 `docs/RISK_REGISTER.md`；关键取舍写入 `docs/adr/`。

## B. 创建主工程

- 使用 Godot 4.7.2 Stable + GDScript 的候选技术基线，允许审查后报告版本安装障碍。
- 建立项目入口、合理目录、`.gitignore`、`README.md`、基本 `AGENTS.md`、Git（如已有仓库则沿用），不擅自创建远程仓库。
- 保持最小结构，可实际运行；不提前生成大量空系统。

## C. 第一层级地图（真实可复用模块）

- 地图作为启动后的主要导航入口，临时几何图形/文字表示建筑。
- 创建三个示例建筑：**宿舍（可进入）**、**学校（可进入）**、**商店（锁定，有反馈）**。这只是技术样例，不是正式内容决定。
- 宿舍、学校分别进入独立的临时场景，至少具备一个简单交互和返回地图能力。
- 建筑配置有稳定 ID、名称、地图展示位置、目的场景、开放状态；优先采用 Godot 原生 Resource 或简明数据格式。
- 支持多次进入/退出、无效建筑 ID、缺失场景路径、重复点击防护，并恢复必要的地图导航状态。
- 不实施正式城市地图、美术、NPC、任务、经营系统和复杂建筑解锁。

## D. 适配与输入

- PC **横屏优先**，手机 **竖屏优先**；建筑数据与导航逻辑必须复用，布局/视口/相机允许不同方案。
- 不允许仅通过强制拉伸整张地图适配两种方向。
- 使用 Godot Control 容器与适当布局策略；处理手机安全区域和不可点击热点。
- 鼠标、触摸支持；避免同一触摸事件触发两次导航。
- 最少覆盖以下代表性逻辑尺寸/比例：1920×1080、1280×800、1080×1920、1170×2532。
- 模拟视口测试与设备测试必须分开标记。

## E. 测试与证据

- 尝试真实启动、导入和运行 Godot 项目，检查脚本解析、场景路径及导航。
- 验证：地图进入宿舍→返回；进入学校→返回；商店锁定提示；无效 ID 防护；多次导航无异常；改变窗口比例仍可访问所有建筑。
- 具备对应环境时进行 PC、Android、iOS 构建或运行验证；不具备 SDK、Mac、Xcode、签名或测试设备时，标记为明确未验证。
- 记录**实际测试命令、环境、输出结果、失败项**；不可捏造通过记录。

## F. 不在此次开发范围

- 正式宿舍房间、美术、找猫、整理小游戏、学习系统、NPC、剧情、经济/商店、宠物成长、复杂存档、云服务、完整小游戏宿主。
- 不构建支持所有未来设想的通用框架，不推送远程代码或购买服务。

## 交付与验收

提交：`docs/TECH_FEASIBILITY.md`、`docs/RISK_REGISTER.md`、必要 `docs/adr/*`、可运行 Godot 工程、基础测试、项目运行说明，以及中文交付报告。

**通过条件：** 主要风险有分类和验证路线；主工程实际可运行；两栋建筑进出正常；锁定和无效建筑处理正常；电脑横屏与手机竖屏进行了清楚标注的布局检查；所有未在真机上执行的测试都如实标为未验证。

本任务完成后停止，不自动进入 P0-02。下一步开发由项目负责人确认。
